# Verification of the October 2026 audit fixes

**What this is.** The "Verification and report" step of [FIX-PLAN-2026-10.md](FIX-PLAN-2026-10.md). Every finding of
[AUDIT-2026-10.md](AUDIT-2026-10.md) was re-checked against main at 1ba6623 (all four fix waves merged), using the auditors'
own repro inputs and probes where they exist. The audited main was d2eb914.

**How.**
- The repro inputs from `sfrs-wt/audit-security/audit/repro/`, the fuzz crash input and the static auditor's probes were
  copied into a scratch worktree and run against main through `crates/sf-ffi/examples/limits_probe.rs` (a 512 KiB thread,
  stricter than the app's 8 MiB loader thread) and an uncommitted probe test. Peak RSS comes from `/usr/bin/time -l`.
- The concurrency auditor's `audit_stress`, `audit_leak` and `AuditLeakTests.swift` were re-run unchanged, except for
  `.unwrap()` on the exports that now throw. They still pass `"{}"` options, as the audit did, so the numbers compare.
- Anything that could crash ran in a child process or a CLI probe, never in the app or the test host.
- The machine was idle apart from this work: the 1-minute load average is given next to each timing table.
- The orchestrator ran `just gate` (green: 1762 Rust tests, 580 app tests) and the UI suite (31/31) on 1ba6623.

Status values:
- **Fixed**: the repro no longer reproduces; the evidence column gives before → now.
- **Accepted**: left as the plan decided; the plan line is cited.
- **Open**: the finding still reproduces, at least in part. None regressed.

## Still open

1. **X-07 (Medium): a build after "Load anyway" on an absurdly large part runs away, and Cancel doesn't stop it.**
   - Repro: `limits_probe`-style load with `LoadOptions { allow_large: true }` of the audit's `coupon_one_1e30.stl`
     (1,912 triangles, one vertex at x = 1e30), then `build_part_cancellable(.., "{}", "{}", cancel)`.
   - Result: RSS passes 4.3 GB within 3 s. With the cancel flag raised at 500 ms it still reached 6.4 GB at 4 s, when the
     watchdog killed it. `coupon_scaled_1e5.stl` (7.6 km) reached 7.1 GB in 1 s.
   - Stack (`sample`): `build_part_cancellable` → `build_fins_cancellable` → `build_fins_core` → `fins::pad::build_pad`
     → `fins::pad::brim_pad`, growing an `IndexMap` entry (`or_default().extend`).
   - Location: `crates/sf-engine/src/fins/pad.rs:521-534`. Bucketing the first-layer outline steps `bi`/`bj` by 1.0 over
     0.5 mm buckets across the segment's extent, so 2e30 buckets for this part. Past about 2^53, `bi += 1.0` stops
     advancing, so the loop never ends. `cfg.cancel.check()` runs only once per outline segment (line 522), not inside
     the two inner loops. 2D's guards (`guards::MAX_STEPS`, `too_many_steps`) cover `tracks.rs`, `endrows.rs` and
     `footprint.rs`, but not this loop.
   - Reach: the user must accept the "Load anyway?" prompt for a part over 2 m, then turn fins on.
   - Not fixed here, by instruction.
2. **The CLI still reads STEP in-process** (`sf-cli` default feature `occt`), so a malformed STEP still segfaults the
   CLI and any `occt` test build. This is by design (#220: "a crash ends only the CLI").
3. **Swift ASan cannot run the STEP helper** (3 `StepReaderTests` failures; see Sanitizers). This is a gap in tooling
   rather than a finding.
4. **Deferred to the hygiene sweep, as planned:** the 21 Swift warnings (C-10, S-09, including the ignored drop
   result), `cmp_diff` ×6 and the other duplicated helpers and dead code (S-12), and `ParkedWalls` at `.utility` (C-09).
