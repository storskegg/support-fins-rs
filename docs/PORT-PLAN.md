# Support Fins → native macOS: port plan

Source: `gittrahan/support-fins` (mirrored at `storskegg/support-fins`), pinned at
**`9f643a4`** (2026-10-26). Target: one machine — Apple M2 Max, 12 cores, 96 GB,
macOS 26.x, Xcode 27, Swift 6.4, Rust 1.99.1. Personal use.

This document is the plan. Tickets (GitHub issues on `storskegg/support-fins-rs`) are cut
from it one milestone at a time; this file stays the source of truth for *why*.

---

## 1. Decisions (settled)

| topic | decision |
|---|---|
| Engine | Rust, Rayon for data parallelism. Pure maths, no UI. |
| Front end | Swift 6 (SwiftUI + AppKit where SwiftUI falls short) + Metal (Metal 4 APIs where useful). |
| Swift ↔ Rust | **In-process**, Rust built as a static library, interface generated by **UniFFI** (Swift bindings). Bulk geometry crosses as raw pointers into page-aligned Rust allocations wrapped by `MTLDevice.makeBuffer(bytesNoCopy:)` — zero copy on unified memory. Long work runs as **jobs** with progress callbacks and a cancel token. No separate process, no serialisation of meshes. |
| Fidelity | Match the JS maths as closely as possible: same structure (walls, tines, records, counts) and vertices within **1e-6 mm**. An algorithm may deviate only if it is shown to beat JS; the criteria for "beat" are deliberately open and get settled when we reach testing. Until then: **no improvements, only a port.** |
| Acceptance | **The Rust port is accepted when it passes the ported unit tests.** Every JS test file is ported in full: every case and every assertion, with nothing skipped or loosened. Rust adds its own thorough unit tests on top. Oracle parity is the diagnostic that explains *why* a test fails, but the ported tests are the bar. |
| Repo shape | A Cargo workspace of library crates plus binaries (CLI, oracle tools), and the Xcode app beside it (§3). |
| Scope | Full feature parity with the web app. |
| UI | As faithful to the web layout as possible while being a proper Mac app (menu bar, inspector, toolbar, keyboard, trackpad, documents). |
| Dropped | Phone layout, tap gestures, WebGL failure guards, PWA/deploy files (Docker, nginx, wrangler, `_headers`), in-page plugin loader. |
| Kept / changed | Tips → native popovers/tips; tutorial → macOS Help Book; 11 languages → String Catalogs; 3MF sessions readable/writable **both ways** with the web app. |
| STEP | Native **OpenCascade**, pinned to the version occt-import-js 0.0.23 was built from, same tessellation parameters. |
| Booleans | **Manifold 3.5.4** (the vendored version) through its official C API (`manifoldc`) via `bindgen`. |
| Integrations | Ship a Rust **CLI** with the same flags as `plugins/cli` (generated from `options.json`). Host plugins (Blender, Fusion, …) stay on the JS engine. |
| Upstream | **Frozen at `299ef49` until full feature parity (M7).** Decided by the user on 2026-10-27: no milestone-boundary catch-ups until then, so the first goal isn't a moving target. After parity, catch up in one pass, then at each later milestone. The JS checkout must stay at the `UPSTREAM` commit. |
| Process | **Four** Sonnet 5.5 (medium) agents (two in M3–M4a to stay within usage limits; back to four from M4b, 2026-10-27) write the code in their own worktrees and open PRs. The orchestrator writes briefs, reviews, merges. Two failed reviews on one ticket → re-assigned to Opus, and the user is alerted. All four work within a milestone. **Four agents when writing code, two when measuring** (benchmarks and timing runs, so they do not disturb each other's numbers). Since 2026-10-28 the orchestrator no longer pauses for the user's go-ahead at milestones: it carries on until the port is complete, and still posts a milestone report at each one. |
| Reporting | Written report at every milestone (landed, parity, perf vs JS, known gaps). Demo build at the major ones: **M3** engine done, **M4** app usable, **M7** full parity. |

### Performance targets (starting values, revised once measured)
- Orbit/pan/zoom a 1M+ triangle part at a steady **120 fps** (ProMotion).
- **Live Auto rebuild while dragging** the pose: typical part < ~50 ms per build.
- `flat_bracket.stl` laid flat (JS ≈ 2.4 s): **< 150 ms**.
- Suggest orientation: **10× the candidate poses** of the web app, in less wall time.
- Load + weld a 1.5M-face STL in well under a second.

### Hazards the briefs must spell out
These are where a faithful-looking port quietly gives different numbers:

1. **Global mutable config.** `PROP`, `FIN`, `CUT`, `ISLAND`, `DOWNHILL`, `RIM`, `CURVED`, `ARC`,
   `TIE`, `JUDGE`, `FIELD`, `PAD` are module-level objects that `applyTunables` writes before
   each build. In Rust: one immutable `Tunables` value built once per build and passed down
   explicitly. Nothing global, ever: parallel builds must not see each other's settings.
2. **Per-mesh caches** (`WeakMap`s in surface, trace, nearface, judge, circular, seating, sway;
   module `let`s in crest, brace). In Rust: lazily built, thread-safe caches owned by the
   `Topology` (or by the per-build context when they depend on pose or settings). Same
   contents, same lifetime semantics.
3. **Float semantics.** JS numbers are f64, so Rust uses f64. Do **not** "tidy" expression
   order (`a*b+c` ≠ `mul_add`, and reassociating a sum changes bits). The `jsnum` module provides
   JS-identical helpers, and agents must use them:
   - `Math.round` rounds .5 up, toward +∞. `f64::round` rounds it away from zero.
   - V8 15.0.245's `Math.sin/cos/tan/asin/acos/atan/atan2/exp/log*/cbrt` are **LLVM libc**
     (with FMA), ported bit-exact into `jsnum::llvm` (#2). `Math.pow` is V8's wrapper around the
     **platform** `pow`, so `jsnum::pow` is bit-exact on macOS arm64 only. That's a recorded platform
     dependency, and fine for this project's single target.
   - `|0`, `>>>`, `Math.imul`, `Math.trunc`, `Math.sign(-0)`, `Math.min/max` with NaN and -0,
     and `toFixed` for 3MF/STL text.
4. **Order.** `Map`/`Set` iterate in insertion order, so use `IndexMap`/`IndexSet`.
   `Array.prototype.sort` is stable, and so is `sort_by`. But a comparator that returns NaN or is
   inconsistent must be reproduced exactly as JS treats it.
5. **Parallelism must not change output.** It goes in after parity is locked. Each parallel stage
   reduces in input order, and the results stay identical to the serial port.
6. **Rotations come from three.js** (`Quaternion`, Euler XYZ, `Matrix3` column-major). Port the
   exact three.js routines used (`setFromEuler`, `makeRotationFromQuaternion`, …) into
   `sf-engine::three`, line by line, so a CLI `--rot` matches the site bit for bit.

## 4. The parity system (the backbone)

Agents never port "by eye" and hope. Every ported function is checked against the JS one
by running both on the same inputs.

1. **Oracle (Deno).** For each JS function being ported, `parity/oracle/<module>.js` imports
   the real module at the pin. It runs the function over a list of inputs: fixtures × poses ×
   tunables, plus the arguments captured from real `buildFins` runs. It writes `{input, output}`
   cases to `parity/corpus/<module>/`. Capture mode wraps exports by renaming them, as
   `docs/PERFORMANCE-SPEC.md` already does, and records real call arguments. That way the inputs
   to low-level functions are the ones they actually see.
2. **Replay (Rust).** `cargo test -p parity` loads each case, calls the Rust function, and
   compares:
   - discrete outputs (counts, indices, booleans, records) must be **equal**;
   - floats must be within **1e-6 mm** (absolute) or 1e-9 (relative), whichever is looser.
3. **First-divergence tracing.** When a whole build differs, the harness replays the
   captured calls in order and reports the **first** function whose output differs. That
   function is the bug.
4. **Ported tests.** Each `tests/*.test.js` becomes a Rust test with the same name and
   assertions. These are the acceptance gate (§4a), and replay is how a failure is diagnosed.
5. **Golden scenes.** The `tests/golden/` scenes are re-recorded through the oracle as full
   builds and compared within the tolerance. They are not compared by hash.
6. **Corpus.** Covers `tests/fixtures`, `prototype/stress/models`, the `prototype/calibration` coupons,
   `flat_bracket.stl` if we can obtain it, and the scenes in `tests/_scene.js`. Poses come from
   `sitePose`.

Upstream catch-up reruns the oracle at the new pin. The cases that change show exactly
which Rust code has to follow.

### 4a. Unit tests (the acceptance gate)

- **The port is 1:1.** `tests/foo.test.js` becomes `crates/sf-engine/tests/foo.rs` (or the crate
  that owns the module). Each `Deno.test` becomes one `#[test]` with the same name in
  snake_case, and each `assert*` becomes an assertion on the same value. The JS file and line go
  in a comment above each test.
- **Nothing is loosened.** An exact JS comparison stays exact. A JS tolerance stays the same
  tolerance. A test may only change if the change is listed in the PR's **Divergences** section
  and the orchestrator approves it. Failing tests are never `#[ignore]`d to land a PR.
- **The original must still pass.** Each ported file records the JS test it came from. CI runs
  `deno test` on that file at the pin, so a ported test can't be checking for something the JS
  never claimed.
- **Rust adds its own tests on top.** Each ported function gets unit tests for its edges:
  degenerate and zero-area triangles, -0, NaN, empty input, a single face, exact-threshold
  faces (`ANGLE_EPS`), and points on grid-cell boundaries. Properties such as "the gap is
  preserved" and "no wall is inside the part" get property-based tests (`proptest`) over the
  fixture set.
- **Test map.** `docs/TEST-MAP.md` (written in M0) lists each of the 82 JS test files with the
  modules it exercises, the milestone that must turn it green, and its current status
  (not ported / ported-red / green). The milestone exit criteria are read off this table.
- **Test helpers** live in `crates/sf-testkit`, ported from `tests/_util.js`, `_scene.js`,
  `_bore.js`, `_circular.js` and `_occt.js`. It's a dev-dependency only.

## 5. Milestones

Each milestone ends with a written report. Since 2026-10-28 there is no pause for the user's go-ahead (see the Process row in §1): work continues straight into the next milestone. Upstream catch-ups are paused until M7 (see §1).
Tracks **A–D** are the four agents. Agents rotate between tracks; the track is the work, not the agent.

**The maths comes first.** M0–M3 are engine-only: all four agents port maths, file formats
and tests. No Swift, Metal or FFI work starts until the engine passes its ported tests (M3).
The app is then built on a finished, tested engine instead of a moving one.

### M0 — Foundations (the maths' footing)
- **Orchestrator:** GitHub repo (private) and push; `docs/AGENTS.md` (brief and PR rules, below);
  issue templates; `UPSTREAM`; the test-port map (§4a), which pairs each JS test file with the
  milestone and the module it gates.
- **A:** Cargo workspace and crate skeletons; `jsnum` (every helper in Hazard 3, each with
  exhaustive tests against values recorded from V8: halves, -0, NaN, ±∞, subnormals, 2^31 and
  2^32 edges).
- **B:** `sf-engine::three` (the Euler, Quaternion and Matrix3 routines the engine and tests use),
  with the same values recorded from V8; `sitePose` from `tests/_scene.js`.
- **C:** Parity system v1: the oracle runner, capture-by-rename, corpus format, Rust replay
  harness, `just oracle` and `just parity`. The first recorders are `jsnum` and `three` (shared
  with A and B), then `overhangs.js` (`buildTopology` and `analyze`), ready for M1 to replay.
- **D:** Test-port harness: the Rust equivalents of `tests/_util.js`, `_scene.js`, `_bore.js`,
  `_circular.js` and `_occt.js` (fixture loading, `siteOpts`, synthetic solids), plus a
  `deno test` runner at the pin, so every ported test can be checked against the JS original.
  The minimal STL reader needed to load fixtures moves forward from M1.

**Exit:** `just check` runs fmt, clippy, unit tests and parity, all green. `jsnum` and `three` match
V8 bit for bit through the parity replay. The `overhangs.js` cases are recorded.

### M1 — Engine layers L0–L1 and file formats
- **A:** geometry: topology and weld (`buildTopology`), `analyze`, gridsize, inside
  (`insidePart`, `nearestPart`, `solidClearance`), planes, islands, pieces, solids, kiss.
- **B:** the prop and fins configs, `Tunables` and `applyTunables` semantics, surface, seating,
  nearface, mold, contact, trace, crest, rival, ties, brace, resinfoot, cutout, nozzle, materials.
- **C:** judge, `prop/downhill`, `fins/field`, `prop/curved`, drawarc; then `sf-io`: STL (binary and
  ASCII), OBJ, zip, 3MF read and write (geometry, then sessions), exportname, paintcode, scale.
  Exports must byte-compare with JS for identical input.
- **D:** tests and parity for M1. D ports the JS test files `docs/TEST-MAP.md` assigns to M1
  (`weld`, `stl`, `obj`, `scale`, `nearface`, `surface_lowest`, `trace`) and writes the oracle
  recorders for every module A, B and C port. Writing tests in their own track keeps a test from
  being bent to fit the code it checks. Most JS test files go through `buildFins`, so they gate M3
  (see TEST-MAP).

**Exit:** the ported tests for every L0–L1 module pass, and parity is green for those modules.

### M2 — The prop pipeline (L2–L3)
- **A, B, C** split L2 and L3: sweep, clearance, bridge, arc, circular, pins, rim, bridgerace,
  coverage, tracks, tines, attached, squat, raster, lattice. Then `prop.js` (`buildProps`,
  `buildShortWalls`).
- **D:** ports the M2 rows of TEST-MAP (`must_class`, `neck`), and writes the oracle recorders
  and capture-mode cases for the L2 and L3 modules, so `buildProps`' internals replay from real
  builds.

**Exit:** `buildProps` matches the oracle on the full corpus, and its ported tests pass.

### M3 — buildFins complete (major: engine done)
- **A, B, C:** `fins/*` (rows, pad, wedges, tall, shortwalls, downhill, fill), `sway`, `draw` and
  `drawarc`, `fins.js`, `orient.js` (suggest, layerVerdict, strength pose). Then **sf-cli** with
  the same flags (generated from `options.json`), JSON output, and 3MF out.
- **All four** port the ~60 M3 rows of TEST-MAP as soon as their modules land. That includes
  `golden`, `stability` and `integration`, and the CLI's tests. No agent ports the tests for a
  module it ported itself.
- **Exit:** all 82 test files are ported and pass. The golden scenes match within the
  tolerance. CLI output matches the JS CLI on the corpus.
- **Report:** a serial-Rust vs JS timing table. **Demo:** the CLI on your own parts.

### M4 — App foundations and core loop (major: app usable)

Split into **M4a** (FFI, app skeleton, a viewer with live overhang shading) and **M4b** (the core loop),
with a checkpoint between them. The interface is specified in `docs/FFI.md`.
- **FFI:** `sf-ffi` via UniFFI → a Swift package. Zero-copy vertex and index buffers from Rust into
  `MTLBuffer` (`bytesNoCopy`, page-aligned). A job system with progress, cancel and
  generation counters.
- **App skeleton:** a document-based app with a Metal view (`MTKView` or `CAMetalLayer`), orbit,
  pan and zoom in Z-up millimetres, the plate grid, printer volume presets, ProMotion pacing,
  and GPU ID-buffer picking.
- **Core loop:**
  - load STL, OBJ or 3MF; overhang shading from Rust `analyze`; the stats bar;
  - the rotate gizmo (rings, 5° snap), lay-face-on-plate, the live readout, undo and redo;
  - Auto build as a cancellable job; rendering the fins, pad and tines; per-fin selection and
    removal;
  - export STL and 3MF;
  - the settings inspector, with the web form's sections and fields in the same order;
  - materials and nozzle; the strength overlay and load arrow; the suggest orientation UI.
- **Demo:** the full load → orient → Auto → export loop.

### M5 — Performance
- Profile first (Instruments, `cargo flamegraph`), following `docs/PERFORMANCE-SPEC.md`.
- Rayon over walls, stations, candidates and suggest poses. Each reduces deterministically,
  so parity stays green with no tolerance change.
- Incremental and cancellable builds, so a rebuild can abandon a stale pose mid-way. Live
  rebuild while dragging. Double-buffered GPU geometry.
- SIMD where the profile says so (e.g. `inside` ray parity). Wide suggest search.
- Metal: instancing for tines, indirect draws, a 1M+ triangle stress scene at 120 fps.

**Exit:** the performance targets in §1 are met, or the report explains why not.

### M6 — Remaining tools
- Draw mode: walls, arcs, sway Draw, braceghost. Remove, the section plane, move, arrange, and
  multi-plate (plates, platerow, plateview).
- Cut and cutout (`sf-cut`, Manifold). STEP (`sf-step`, OpenCascade, version-matched; tessellation
  parity on `tests/fixtures/*.step`).
- Calibration coupons, islands UI, footprint, view cube, camera presets, search.

### M7 — Full parity and polish (major)
- 3MF sessions round-trip with the web app, in both directions, on a corpus of sessions saved by the web app.
- 11 languages (String Catalog, generated from `web/i18n/*.js`). Tips. Help Book from the web
  tutorial pages.
- A pass over the menu bar, keyboard shortcuts and trackpad gestures.
- **Demo:** side by side with the web app on your own parts.

Upstream catch-ups are paused until full parity (M7). After that, one catch-up pass brings in everything that changed upstream.

## 6. How agents work (summary of `docs/AGENTS.md`)

**A brief** (one GitHub issue) always contains:
- the exact JS files and functions in scope, with line ranges, at the pinned commit;
- the Rust module and its public signatures, written by the orchestrator. Agents do not design
  interfaces;
- the parity cases to record, and which ported tests must pass;
- the hazards that apply (from §2) and the parts of the code that are explicitly out of scope;
- the Definition of Done.

**Rules for agents:**
1. Port; don't redesign. Keep the JS function's structure and names (in snake_case) and its
   comments' reasoning. Each Rust function's doc comment cites its JS origin (`web/prop/sweep.js:42`).
2. Never invent constants, thresholds or behaviour. When the JS is unclear, stop and ask in the PR
   instead of guessing.
3. No performance work before M5 except in code that is new by nature (the FFI and the
   renderer).
4. Every ported function has oracle cases. "Tests pass" means `just check` passes, including
   `parity`.
5. The PR body has: Scope, JS origin, Parity results, a **Divergences** section (any line that
   is not a literal port, and why), and any open questions.

**Review (orchestrator):** read the diff against the JS line by line for anything in scope.
Check for hazard violations, tidied arithmetic, invented branches, and holes in test coverage.
Review comments are concrete: the file and line, what is wrong, what JS does, and what to do instead.

**Escalation:** a ticket whose PR fails review twice is re-assigned to an Opus agent. The user
gets a push notification, and the PR and issue are labelled `escalated`.

## 7. Risks

| risk | mitigation |
|---|---|
| Float drift flips a discrete decision (the JS stability test shows these sit near thresholds) | fdlibm via `libm`, `jsnum`, no reassociation, and first-divergence tracing that lands on the exact function |
| OpenCascade version or tessellation mismatch | pin the version occt-import-js uses; tessellation parity cases; fall back to building OpenCascade from source |
| Agents guess at unclear JS | signatures come from the orchestrator; a "stop and ask" rule; oracle cases make guessing visible |
| Upstream moves fast | catch-up at each boundary; the oracle diff shows which cases changed |
| Parallelism changes results | ordered reductions; parity is the gate for M5 |
| Metal and SwiftUI interop at 120 fps | an `MTKView` or `CAMetalLayer` in an `NSViewRepresentable`; the renderer owns its own frame loop, separate from SwiftUI state |
