# Audit, October 2026: concurrency, static analysis, security

**Scope.** main at d2eb914, the port after full parity (M7) and the upstream catch-up to 23039e2. The audit only reports: no code was changed. Its purpose is to feed a fix plan that the user and the orchestrator will draw up together.

**How it was done.** Three Opus auditors worked in parallel, each in its own worktree, with sanitizers, fuzzers and lints. The orchestrator then re-checked the worst findings. The detailed findings, with evidence, repro steps and measurements, are in:
- [audit-2026-10/concurrency.md](audit-2026-10/concurrency.md) (C-01 to C-11)
- [audit-2026-10/static.md](audit-2026-10/static.md) (S-01 to S-13)
- [audit-2026-10/security.md](audit-2026-10/security.md) (X-01 to X-15)

Repro inputs and probes stay in the auditors' worktrees, which are not in git: `sfrs-wt/audit-{concurrency,static,security}`.

**Counts.**

| Area | Critical | High | Medium | Low | Info |
|---|---|---|---|---|---|
| Concurrency and resources | 0 | 2 | 3 | 3 | 3 |
| Static analysis | 0 | 1 | 6 | 3 | 3 |

There are no Critical findings. Under the threat model (a single-user, sandboxed desktop app whose realistic attacker is a downloaded model file), the worst outcomes are a crash of the whole app, a hang, or memory exhaustion. Nothing points to code execution or data leaving the machine.

**Re-checked by the orchestrator:**
- X-01: the CLI exits with SIGSEGV on a mutated STEP file.
- X-02: the CLI aborts with "stack overflow" on a 114 KB 3MF with deeply chained components. The app overflows at about 400 levels, because it loads on a 512 KiB thread.
- C-01 and C-02: today's 11 test-host crash reports are 9 in `PlateBoard.session`, 1 in `PlateBoard.go` and 1 in `DrawModel.controller`, all `swift_abortRetainUnowned`. The strong `[host]` capture is at `SuggestFeature.swift:32`.
- S-01, S-04 and S-06: confirmed at the cited lines.

## Themes, ranked

Findings are grouped by what a fix would touch. Related IDs across the three areas are merged into one theme.

### T1. Window lifetime: a leak that hides crashes (High)
**C-01, C-02, S-13**
- **The leak:** every window that showed a part leaks. The retain cycle is ViewerModel → toolbar → the Suggest closure's strong `[host]`. Memory grows about 115 MB per closed window on a 320k-face part, and the part, its builds, Metal buffers and three worker threads all stay alive.
- **What it hides:** 25 Feature/model classes hold `unowned let host`, and some `Task`s outlive the window. When the window really goes, these crash with `swift_abortRetainUnowned`. Today's 11 crash dialogs were exactly this, triggered by an agent's interim attempt to break the cycle.
- **Constraint:** C-01 and C-02 must be fixed together. Fixing the leak alone turns it into crashes.

### T2. Untrusted files that crash the whole app (High)
**X-01, X-02, X-05, S-02, X-11/C-06, X-12**
- **X-01:** a malformed STEP file segfaults inside OpenCascade, in-process; 104 of 325 small mutations crash. The C++ shim's `catch(...)` can't catch a signal. STEP is detected by content, so any extension works. The web (WASM) survives the same files.
- **X-02:** a 3 KB 3MF with a 400-deep component chain overflows the 512 KiB load thread's stack.
- **X-05:** a 1.4 KB 3MF whose embedded session JSON is nested 1600 deep overflows the stack.
- **S-02:** a malformed Bambu `model_settings.config` panics the 3MF reader. The app turns it into an error ("no entry found for key"); the CLI exits 101.
- **X-11 / C-06:** 58–82 non-throwing UniFFI exports turn any Rust panic into an app abort. A panicking listener callback silently kills a worker, and no builds land after that.

### T3. Untrusted files that exhaust memory or CPU (High/Medium)
**X-03, X-04, X-06, X-07, S-05, S-06, S-03**
- **X-03:** 3MF component fan-out has no ceiling. A 969-byte file expands to 10M triangles (2.9 GB); a 990-byte one would need about 290 GB. A load can't be cancelled.
- **X-04:** the ZIP reader has no decompressed-size limit and accepts overlapping central-directory records (3 MB → 3.2 GB; 1 MB → 4.3 GB, unbounded).
- **X-06:** JSON object parsing is quadratic (460 KB session → 33 s hang).
- **X-07:** NaN, inf and absurd coordinates are accepted. One vertex at 1e30 drove a build past 32 GB.
- **S-05:** footprint grids are sized by the bounding box in mm² on the main thread. A 20 m part costs 6.8 s and 400 MB; around 1e7 mm the allocation can't be caught and the app aborts.
- **S-06:** one vertex at 1e16 makes Suggest loop forever (`tracks.rs` `v += 0.25` stops advancing), and the loop never checks cancel.
- **S-03:** NaN-tolerant sort comparators can panic in Rust ≥ 1.81. Proven in a probe; no route through the engine found yet.

### T4. Responsiveness and resource use on big parts (Medium)
**C-03, C-04, C-05, C-07, C-08, C-11**
- **C-03:** export runs synchronously on the main thread: 4.3 s for an Earth Focus object (772k faces), 7.4 s for 1.2M faces. Plate exports also build Draw walls on the main thread.
- **C-04:** Suggest and Strength searches are never cancelled when their window, part or popover goes, and they slowed a concurrent build from 642 to 1144 ms. The builder doesn't cancel on drop.
- **C-05:** opening the private 3MF (10 objects, 7.7M faces) peaks at 4.8 GB, and every object becomes a GPU mesh before the object picker appears.
- **C-07:** each build result stores the fins three times.
- **C-08:** click-time engine calls take up to 118–294 ms on the main thread.
- **C-11:** per-thread stamp arrays stay on the Rayon workers for the life of the process.

### T5. What the user sees when something fails (High)
**S-01**
A failed open shows a Swift debug dump such as `SupportFinsCore.FfiError.Format(message: "no triangles in the file")`, where the web shows "Could not read X: …". `FfiError` has no `LocalizedError`, and `localizedDescription` is used in 5 places. No test checks error text.

### T6. Test and gate gaps (Medium)
**S-04, S-07, S-08**
- **S-04:** `just gate` runs app tests only when `app/` or `crates/sf-ffi/` changed (`tools/gate/gate.py:46`). There's no CI behind the gate, and Swift warnings aren't gated.
- **S-07:** tests still pass `"{}"` where the app sends real JSON (80 Rust sites, most Swift Suggest/Export/Build tests). This is the class that hid the Suggest break. Rust doesn't validate tunables at all (wallLines 1e9, nozzle 0 and pinDepth −1 all build).
- **S-08:** accessibility identifiers sit on plain containers, the bug class seen in #204 and #206. Unverified, because UI tests were off-limits to the auditors.

### T7. Writing files (Low)
**X-08, X-09, X-10/S-11**
- **X-08:** "All plates" zip entry names come from untrusted object names, path traversal included. Zip extractors usually sanitise these, but we shouldn't rely on that.
- **X-09:** exports and calibration copies aren't atomic, so a failed write destroys the old file.
- **X-10 / S-11:** the ZIP and STL writers silently wrap or truncate past 4 GiB.

### T8. Hygiene and housekeeping (Low/Info)
**S-09, C-10, C-09, S-10, S-12, X-13, X-14, X-15**
- **Warnings:** 21 Swift compiler warnings (S-09), including a drop handler whose "reject" result is ignored. 3 Swift 6 concurrency warnings remain (C-10).
- **C-09:** the reported QoS inversion is most likely the UI-test runner, not the app.
- **S-10:** `precondition`/`JSONSerialization` crash on a NaN.
- **S-12:** the M4a section of FFI.md is stale, about 35 items are unused (Periphery), and small helpers are duplicated (`cmp_diff` ×6, union-find ×6). Clippy pedantic/nursery/restriction: 10,556 non-test hits, triaged in static.md.
- **X-13:** OpenCascade prints to stdout.
- **X-15:** the `SFChangelogFixture` test hook still works in release builds.
- **X-14, dependencies and licences:**
  - cargo-audit: clean, apart from `basic-toml` being unmaintained (build-time only).
  - There is no `deny.toml`.
  - **OpenCascade (LGPL-2.1) is linked statically, which carries relinking obligations if the app is distributed.**
  - uniffi is MPL-2.0 and needs a notice.

## What's solid (leave it alone)

**Concurrency core**
- Cancellation and generation counters are sound.
- No lock is held across a cancel point or a Rayon join.
- Rust threads never wait on the main thread.
- No thread explosion: one thread per builder or suggester.

**Sanitizers**
- Rust TSan and ASan: 0 reports, including 3×200 rebuilds with cancels.
- Swift TSan: 0 warnings on 65 app tests.

**Memory**
- No Rust-side leak: RSS flattens over 100 Earth Focus builds.

**FFI argument checking**
- Rotation, threshold, dialog/export options and session fields are all checked.
- File-reading FFI calls throw, and both worker threads catch panics.

**Readers**
- STL and OBJ survived 4.7M and 2.6M fuzz inputs; about 20M fuzz executions in all across six targets.
- The ZIP reader is bounds-checked and never extracts to disk.
- There's no XML entity expansion.
- Out-of-range triangle indices are dropped.

**Security posture**
- App Sandbox and Hardened Runtime are on, with only user-selected read-write access and no network entitlement.
- All URLs are hard-coded https, and the problem report sends no paths.
- No `Process`, `dlopen` or web view.

**Code**
- Few force unwraps, and no `try!` or `as!` outside generated code.
- Default clippy and fmt are clean.

**CLI**
- Project mode writes atomically and refuses symlinked outputs.

## Not checked

- UI tests (they drive the mouse), so S-08 and the QoS warning were not reproduced.
- Swift ASan.
- Miri.
- GPU memory in the running app (Instruments).
- Sanitizer-instrumented C++ (Manifold, OCCT). X-01 was found by structured mutation instead.
- Whether the upstream web shows the same resource blow-ups (T3) in a browser.
- Whether `Builder.cancel` stops the X-07 runaway build.

## Parity constraints for the plan

Engine fixes must keep the JS output identical: the parity corpora and the 77 bench_m5 stress-build hashes must not change. Most T2/T3 fixes are input limits and error paths that sit before or around the engine maths (depth caps, size ceilings, rejecting non-finite coordinates, cancel checks inside loops), so they shouldn't move any parity output. Wherever the JS behaves differently (it throws a catchable error where we abort), the native app should fail safely with a message rather than copy the JS failure.
